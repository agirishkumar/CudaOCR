OCR for printed documents,
with the image work on the GPU.

CudaOCR turns scans, photos of pages and scanned PDFs into text, JSON or hOCR. Cleaning, binarization, deskew and line detection are hand-written CUDA kernels, each checked against a CPU reference implementation. Recognition runs the PP-OCRv5 English model through ONNX Runtime.

Deskew

A Hough transform finds the text angle, and a rotation kernel straightens the page before lines are cut. Only baseline pixels vote: when every ink pixel voted, diagonals through several rows beat the true baselines by up to 3°.

Light text on dark

Polarity is decided on the grayscale image, which is flipped before binarization. Thresholding light-on-dark text directly leaves halos around every glyph.

Engineering notes

Things that went wrong or turned out differently than expected. Each fixed bug has a named regression test, and each tuning choice is backed by a measured sweep, recorded in the decision log.

Build

Compiled for the wrong GPU for five months

The CUDA architecture default was set after project(), so every build silently targeted sm_75 and the driver JIT-compiled PTX at start-up. Nothing failed until toolkit 13.4 produced PTX newer than the 13.2 driver accepts, and 33 of 59 tests broke at once.

Fix: set the default before project() and always embed native code for the target GPU.

CudaArch.CudaArchMatchesDevice
Concurrency

A race only a refactor could see

Uploads and fills ran on the default stream while the kernels ran on the pipeline's own stream, so a kernel could read a buffer before its upload finished. It turned up while checking that the new component-based pipeline matched the old one, box for box.

Fix: every transfer and fill now takes the caller's stream explicitly.

StreamOrdering.*
Numerics

TF32 was moving the answers

With ONNX Runtime's defaults, the CUDA recognizer's character probabilities differed from the CPU run by up to 0.065, enough to flip characters. Turning TF32 off brought the difference down to 1.8e-5.

Correctness first: TF32 is off by default and can be re-enabled in the config.

decision log #24
Memory

A horizontal rule asked for 3.8 GB

A thin ruled line detected as a "text line" has an extreme aspect ratio. Scaled to the recognizer's 48-pixel height, it became a crop wide enough to exhaust a 6 GB card.

Fix: a maximum crop width. Degenerate lines are capped instead of failing the page.

PlanLineCrops.MaxWidthCapsDegenerateAspectRatios
Tuning

One constant, 23 % → 5 %

The adaptive threshold offset C started at 10. A sweep over the synthetic, large and real-scan sets moved real-scan CER from 23.45 % (C = 10) to 5.01 % (C = 40). C = 60 scored marginally better on clean pages, but a low-contrast test page fell apart (99 % CER), so the default stopped at 40.

decision log #25 · Accuracy.* ratchets
Layout

Descenders became their own lines

Row-projection profiles split the tails of g, p and y (and the dots over i) into thin separate "lines". Slivers are now merged into their neighbour, with a test that a genuinely short line between two noise blobs survives.

DetectLines.Merges* · DetectLines.DoesNotSwallowShortLineBetweenNoiseBlobs
Tuning

How much margin a line crop needs

Each line box is padded before it is resized to 48 px. On the synthetic pages, CER was 0.37 % with no padding and 0.25 % with 10 %. At 30 % the crops pulled in neighbouring lines, and the skewed page reached 54 % CER.

decision log #23
Shipping

Works in the build tree, not once installed

The installed binary couldn't find ONNX Runtime or the model. The install now carries both, with an $ORIGIN-relative library path. The CUDA runtime is linked statically, so the binary starts with only the NVIDIA driver present.

Known limitations

The scope is printed, mostly single-column pages. It is meant to be a functional, modular OCR engine, not a state-of-the-art competitor.

  • Multi-column pages, tables and figures. Layout reads one column from top to bottom: 19.6 % CER on full UNLV pages, against 6.8 % when the text regions are given.
  • Heavy stains. Large blots binarize as ink and are read as characters. The coffee-stained sample is at ≈ 30 % CER.
  • Throughput. About 0.3–0.4 s per dense page, almost all of it in the recognizer.
  • Script. English/Latin only (the model's 436-character dictionary). No handwriting or scene text.

Install

Linux x86-64 with an NVIDIA GPU (Turing or newer) and a CUDA 13 driver.

Debian package

Ubuntu 24.04 or 26.04. Download the matching .deb from the releases page. It includes ONNX Runtime and the model.

sudo apt install ./cudaocr_0.1.0-1.ubuntu24.04_amd64.deb
# for GPU recognition
sudo apt install cuda-libraries-13-4 cudnn9-cuda-13

Without the CUDA libraries everything still runs, and --ep cpu recognizes on the CPU.

Docker

Needs the NVIDIA Container Toolkit. The image includes CUDA, cuDNN and the model.

docker build -t cudaocr .
docker run --rm --gpus all \
  -v "$PWD":/data cudaocr scan.pdf -o out/

From source

CUDA Toolkit 13.x, CMake ≥ 3.24, a C++20 compiler; optional libpoppler-cpp-dev for PDFs.

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./scripts/fetch_models.sh
./build/cudaocr page.png
